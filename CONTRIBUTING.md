# Contributing to Yasha

Thanks for helping! This guide covers how to set up a dev environment, run the test suite, and
get a pull request accepted. For the product overview see [README.md](README.md), for
design internals [docs/architecture.md](docs/architecture.md), and for AI-agent guardrails
[AGENTS.md](AGENTS.md).

## Code of conduct

By participating you agree to the [Code of Conduct](CODE_OF_CONDUCT.md).

## Ground rules

- **License**: contributions are licensed under the project's [AGPL-3.0](LICENSE) license —
  by submitting a patch you agree to license your contribution under it.
- **AI assistance is allowed and welcome** — just say so in the PR description (e.g. "with the
  help of AI (MODEL)") and make sure you understand and can defend every line.
- **i18n is mandatory**: every user-facing string goes through next-intl keys present in **both**
  `messages/en.json` and `messages/fr.json` (web) or `res/values/strings.xml` +
  `res/values-fr/strings.xml` (Android). No hardcoded English in components.
- **No personal data in the repo**: keep host-specific facts (URLs, devices, credentials) in
  `AGENTS.local.md` (gitignored) — see [AGENTS.local.md.example](AGENTS.local.md.example).

## Development setup

Everything runs in containers — **no host Node.js required** (and please don't install one):

```bash
cp .env.example .env                                  # edit as needed
cp compose.override.yml.example compose.override.yml  # edit as needed
                                           # uncomment the dev-mode + ports blocks (see header)
docker compose up                          # dev server on http://localhost:3000 (or :80 via Caddy)
```

`docker` can be replaced with `podman` everywhere. One-off commands run inside the dev-stage
`yasha` image (compose auto-merges your gitignored `compose.override.yml`):

```bash
docker compose run --rm yasha <cmd>
# e.g. ... run --rm yasha npx tsc --noEmit
```

## Before submitting — definition of done

All of this must be green:

```bash
docker compose run --rm yasha sh -c 'npx tsc --noEmit && npm run lint && npx vitest run --coverage && npm run build'
```

- **Tests**: the vitest suite (`tests/`) must pass with **100% coverage** of the server scope
  (`app/**/route.ts`, `lib/**/*.ts`, `instrumentation.ts`) — thresholds are enforced in
  `vitest.config.mts`. Any new/changed server route or lib file ships with tests.
- **No coverage pragmas**: if a branch is provably unreachable, delete or simplify it; if it
  guards a real hazard, make it testable instead.
- **Happy path verified interactively** (Playwright for web, emulator/device for the Android app).

Test isolation is strict (throwaway SQLite per test worker, all Lemonade calls mocked — see
`tests/support/`); don't weaken it. `AGENTS.md` documents the harness helpers and gotchas.

Android app: `cd android && docker compose run --rm gradle test lint assembleDebug`.

## Making changes

- Keep PRs focused; describe the *what* and *why*, link issues.
- **Commit messages must follow
  [Conventional Commits](https://www.conventionalcommits.org/)** (`fix: …`, `feat: …`,
  `BREAKING CHANGE:` footer): releases are cut automatically from the commits landing on `main`
  (`docs`/`fix`/`chore`… → patch, `feat` → minor, breaking → major). Your commit messages also
  become the changelog — write them for the release notes, not just for the diff.
- **Do not edit `CHANGELOG.md`** — it is regenerated by CI (git-cliff) on every release.
- Database schema changes: add a generated migration
  (`docker compose run --rm yasha npx drizzle-kit generate`)
  — don't hand-edit SQL in `drizzle/`.
- Environment/config changes: update `.env.example` **and** `docs/configuration.md`.
- Public behaviour changes: update the affected README/docs pages in the same change.

## Reporting issues & asking for help

- Open an issue on the repo tracker (see [SECURITY.md](SECURITY.md) for *security* issues —
  those are **not** public issues).
- Include: Yasha version (or commit), how you run it (compose / single image / own proxy),
  browser/device, and steps to reproduce.

## Roadmap

The project evolves in phases tracked in the issue tracker; pick a `good-first-issue` label to
start. For larger features, open an issue to discuss before writing code.
